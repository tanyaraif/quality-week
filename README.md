# Запись на мероприятия

Статический сайт для записи сотрудников на мероприятия. Хостится на GitHub Pages,
данные хранятся в [Supabase](https://supabase.com) (Postgres + REST API).

## Структура

```
index.html          — точка входа, связывает всё вместе
css/styles.css      — стили
js/config.js        — настройки Supabase (URL + anon-ключ), роли, лимит 3 ч
js/events.js        — мероприятия и слоты
js/api.js           — работа с Supabase (REST) + бизнес-правила
js/app.js           — интерфейс: регистрация, табы графика, «Мои записи»
supabase-setup.sql  — SQL для создания таблиц, политик и тестовых пользователей
```

## Как это работает

1. **Регистрация.** Пользователь вводит персональный ключ (тестовый — `123`).
   Ключ проверяется по таблице `users` в Supabase. Ключ запоминается в браузере —
   при следующем заходе форма откроется автоматически.
2. **Форма по роли.**
   - `service` (сервисная поддержка) — выбирает тип участия: **train** (выход из
     линии) или **личное время**.
   - `tck` (команда ТЦК) — записывается только в слоты ТЦК.
3. **Выбор мероприятия, даты и свободного слота**, затем запись в Supabase.
4. **Лимит:** один ключ может сделать новую запись не чаще, чем раз в 3 часа
   (от последней успешной записи). Иначе показывается, сколько осталось ждать.
5. **Один раз на мероприятие.** Повторная запись на то же мероприятие (любая дата)
   заблокирована.
6. **Табы мероприятий.** На вкладке «Мероприятия» — описание события и таблицы
   записей по датам, которые **автообновляются раз в 30 секунд**. Свои записи
   подсвечены. Вкладка «Мои записи» показывает все ваши слоты.

> Один слот = один человек на каждый тип участия. В один временной интервал могут
> записаться три разных человека: один на train, один в личное время, один из ТЦК
> (если для слота заданы все три типа). У «Своей игры» — фиксированно 2 места для
> сервисной поддержки и 2 для ТЦК.
>
> **Гонка слотов** решается на стороне БД: на `(event_id, date, slot_index, type)`
> стоит UNIQUE-ограничение. Если двое жмут «Записаться» на один слот одновременно,
> второй получит ошибку и увидит «Слот уже занят».

## Настройка Supabase (обязательно для общего доступа)

Пока URL/ключ не заданы, сайт работает в **демо-режиме** — данные сохраняются в
`localStorage` текущего браузера (удобно для локальной проверки, но не общие).

1. Создайте бесплатный проект на https://supabase.com (вход через GitHub).
2. Откройте **SQL Editor → New query**, вставьте содержимое `supabase-setup.sql`
   и нажмите **Run**. Это создаст таблицы `users` и `registrations`, настроит
   политики доступа (RLS) и добавит тестовых пользователей.
3. Откройте **Settings → API** и скопируйте:
   - **Project URL** (вид `https://xxxx.supabase.co`)
   - **anon public** ключ (длинный JWT)
4. Вставьте их в `js/config.js`:
   ```js
   supabase: {
     url: "https://xxxx.supabase.co",
     anonKey: "ваш_anon_ключ",
   },
   ```

> ⚠️ **Про безопасность.** anon-ключ публичный по умолчанию — его можно держать в
> коде. Доступ к данным ограничен политиками Row Level Security: читать `users`
> и `registrations` можно всем, добавлять записи можно, а изменять/удалять чужие
> записи — нельзя (политик update/delete нет). Ключи пользователей в коде не видны.

## Добавление пользователей

Через Supabase: **Table Editor → users → Insert row**, либо SQL:

```sql
insert into public.users (key, last_name, first_name, role) values
  ('a1b2', 'Иванов',  'Иван', 'service'),
  ('c3d4', 'Петрова', 'Анна', 'tck');
```

- `key` — то, что выдаёте человеку в личных сообщениях.
- `role` — `'service'` или `'tck'`.

## Изменение мероприятий

Всё в `js/events.js`. Мероприятия сгруппированы по названию: каждое — объект с
`id`, `title`, `description` и массивом `dates`. Каждая дата содержит `date`
(YYYY-MM-DD), `dateLabel` и свой массив `slots`. У слота: `time` и `types`
(`["train","personal","tck"]` — какие типы доступны).

В табе мероприятия показываются все его даты, у каждой — свой график записей.

## Деплой на GitHub Pages

1. Создайте репозиторий и запушьте файлы (см. ниже про другой аккаунт).
2. В репозитории: **Settings → Pages → Build and deployment**.
3. Source: **Deploy from a branch**, ветка `main`, папка `/ (root)`.
4. Через минуту сайт будет доступен по адресу
   `https://<логин>.github.io/<имя-репозитория>/`.

### Пуш под другим аккаунтом (только для этого проекта)

```bash
git init
git config user.name "ИмяВторогоАккаунта"
git config user.email "email-второго@example.com"
git add .
git commit -m "Сайт записи на мероприятия"
git branch -M main
git remote add origin https://ЛОГИН:PAT@github.com/ЛОГИН/ИМЯ-РЕПО.git
git push -u origin main
```

`PAT` — Personal Access Token второго аккаунта (Settings → Developer settings →
Personal access tokens, право `repo`). `git config` без `--global` меняет автора
только для этой папки.

## Локальная проверка

Просто откройте `index.html` в браузере, либо поднимите локальный сервер:

```bash
python -m http.server 8000
# затем откройте http://localhost:8000
```
